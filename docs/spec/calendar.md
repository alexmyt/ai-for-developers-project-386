# Спецификация: календарь звонков

- **Статус:** действует
- **Дата:** 2026-11-11
- **Область:** роли, правила календаря, слотов и бронирования, API и границы
  тестирования. Форма API описана в TypeSpec-контракте `packages/contract`,
  экраны — в [README](../../README.md).

Документ фиксирует то, что сценарий называет «зафиксированным
в спецификации»: роли, типы встреч, часовой пояс, часы работы, шаг слотов,
окно записи, API и способ проверки. Константы живут в
`apps/api/src/config/calendar.ts`; фронтенд их не дублирует, а получает
через API.

## 1. Роли

- **Владелец** — один заранее заданный профиль. Регистрации, входа и выбора
  профиля нет: админские экраны и владельческие эндпоинты всегда работают
  от имени этого владельца. `ownerId` в API не передаётся.
- **Гость** — любой посетитель без аккаунта. Он выбирает тип встречи,
  свободный слот и оставляет имя с email при бронировании.
- Авторизации нет: все эндпоинты открыты. Это осознанное ограничение
  учебного проекта, а не недосмотр.

## 2. Константы

| Константа | Значение | Смысл |
| --- | --- | --- |
| `TIME_ZONE` | `Europe/Moscow` | Пояс владельца; UTC+3 круглый год, перехода на летнее время нет |
| `WORKDAY_START` | `09:00` | Первый возможный старт слота |
| `WORKDAY_END` | `18:00` | Граница, до которой встреча должна закончиться |
| `SLOT_STEP_MINUTES` | `30` | Шаг между соседними стартами |
| `BOOKING_WINDOW_DAYS` | `14` | Сегодня + 13 следующих дней, включая выходные |
| `MEETING_TYPE_ID_PATTERN` | `^[a-z0-9]+(?:-[a-z0-9]+)*$` | Формат id типа встречи, который задаёт владелец |
| `MEETING_TYPE_ID_MAX_LENGTH` | `50` | Максимальная длина id типа встречи |
| `SEED_MEETING_TYPE_ID` | `intro` | Id сид-типа встречи |
| `SEED_MEETING_TYPE` | «Знакомство», 30 мин | Сид-тип после старта сервиса |

## 3. Время

- В API все моменты передаются как UTC-инстанты в ISO 8601 с `Z`
  (`utcDateTime` в TypeSpec): `2026-11-12T07:00:00Z`.
- Сетка, рабочие часы и группировка по дням считаются в `Europe/Moscow`.
  Пример: `2026-11-12T07:00:00Z` — это `12 ноября, 10:00` по Москве.
- «День» — календарный день в `Europe/Moscow`, интервал
  `[00:00, 24:00)` местного времени.
- Окно записи — 14 календарных дней: сегодня и 13 следующих. Границы окна
  проверяются по московской дате, а не по UTC.
- Текущее время берётся только через `Clock`-провайдер (ADR-0003), поэтому
  тесты не зависят от даты запуска.

## 4. Сетка слотов

Слот — интервал-кандидат, а не запись. Для дня `d` и типа встречи
длительностью `m` слоты строятся так:

```
t = d 09:00
пока t + m <= d 18:00:
    слот(t, t + m)
    t = t + 30 минут
```

- Встреча всегда должна закончиться не позже 18:00, поэтому для типа
  на 30 минут последний старт — 17:30, для типа на 60 минут — 17:00.
- Старты выровнены по сетке от 09:00 с шагом 30 минут. Других стартов нет.
- Слоты, чей старт уже наступил (`start <= now`), в ответ не попадают
  вообще — ни как «Занято», ни как «Свободно».
- Для сегодняшнего дня список может быть пустым: это нормальное состояние,
  а не ошибка.
- День без единого слота всё равно присутствует в ответе — календарь
  всегда показывает 14 дней.

Статус слота:

| Статус | Когда |
| --- | --- |
| `free` | Ни одна бронь не пересекается со слотом |
| `taken` | Есть бронь, пересекающаяся со слотом |

## 5. Пересечения и примыкание

Интервалы полуоткрытые: `[start, end)`. Пересечение:

```
slotStart < bookingEnd && bookingStart < slotEnd
```

- Касание границами конфликтом не считается: встреча 10:00–10:30
  и встреча 10:30–11:00 совместимы. Следующая встреча может начинаться
  ровно в момент окончания предыдущей.
- Частичное наложение запрещено для любых типов встреч: 30-минутная
  и 60-минутная встречи не могут пересекаться.
- Пример из требований: после брони 10:00–11:00 запись с 10:30–11:00
  отклоняется, а запись с 11:00–11:30 допустима.
- Правило действует и при одновременных запросах: проверка пересечений
  и вставка брони выполняются в одной критической секции мьютекса по дате
  (ADR-0003), поэтому успешен ровно один запрос.

## 6. Типы встреч

Создаёт владелец, авторизации нет. Тип встречи — шаблон, который задаёт
размер слота и подпись на гостевой странице.

| Поле | Тип | Ограничения |
| --- | --- | --- |
| `id` | строка | 1–50 символов, `^[a-z0-9]+(?:-[a-z0-9]+)*$`, задаёт владелец, уникален, не меняется |
| `title` | строка | 1–100 символов после trim |
| `description` | строка, опционально | до 500 символов после trim; если не передана или пустая — `null` |
| `durationMinutes` | целое | 30–240, кратно 30 |

- `id` приходит от владельца в форме создания и служит внешним
  идентификатором типа: по нему гость открывает календарь и создаёт бронь.
  Сервер не генерирует id типа встречи.
- Длительность кратна шагу сетки: иначе соседние слоты одного дня
  перекрывали бы друг друга и «число свободных слотов» теряло бы смысл.
- После старта сервиса уже существует сид-тип `intro` — «Знакомство»,
  30 минут, без описания. Он создан тем же способом, что и типы владельца,
  и виден в общем списке.

### 6.1. Создание типа

`POST /api/meeting-types`

```json
{
  "id": "intro",
  "title": "Знакомство",
  "description": null,
  "durationMinutes": 30
}
```

Ответ `201 Created` — созданный тип в том же виде. Ошибки:

| Ситуация | Ответ |
| --- | --- |
| Нет обязательного поля, неверный формат, длительность вне диапазона | `400 validation_error` |
| Тип с таким `id` уже существует | `409 meeting_type_exists` |

Проверки идут в порядке: форма и поля → уникальность `id`.

### 6.2. Список типов

`GET /api/meeting-types`

```json
{
  "items": [
    {
      "id": "intro",
      "title": "Знакомство",
      "description": null,
      "durationMinutes": 30
    }
  ]
}
```

- Сортировка — по времени создания, сначала созданные раньше. Сид-тип
  находится в начале списка.
- Пустой список — `200` и `{ "items": [] }`.
- Эндпоинт общий: его используют и гостевая страница, и админка.

### 6.3. Обновление и удаление

В объёме проекта нет `PATCH` и `DELETE` для типов встреч. `id` и остальные
поля после создания не меняются.

## 7. Доступность

`GET /api/availability?meetingTypeId=intro` отдаёт всё окно записи одним
ответом, чтобы фронтенд не делал 14 запросов:

```json
{
  "meetingTypeId": "intro",
  "days": [
    {
      "date": "2026-11-10",
      "slots": [
        {
          "start": "2026-11-10T06:00:00Z",
          "end": "2026-11-10T06:30:00Z",
          "status": "free"
        }
      ]
    }
  ]
}
```

- `date` — дата в `Europe/Moscow` в формате `YYYY-MM-DD`.
- `days` содержит ровно 14 элементов, начиная с сегодняшнего дня по Москве.
- Неизвестный тип встречи → `404 meeting_type_not_found`.
- Отсутствующий параметр `meetingTypeId` → `400 validation_error`.

## 8. Бронирование

`POST /api/bookings` принимает `meetingTypeId`, `start`, `name`, `email`.
`end` не принимается: длительность берётся из типа встречи, поэтому клиент
не может подделать интервал.

| Поле | Ограничения |
| --- | --- |
| `meetingTypeId` | идентификатор существующего типа, например `intro` |
| `start` | UTC-инстант ISO 8601 с `Z`, старт из сетки внутри окна записи |
| `name` | 1–100 символов после trim |
| `email` | до 254 символов, содержит `@` и точку в домене, без пробелов |

Проверки идут в фиксированном порядке — от него зависят тесты на коды:

1. Форма запроса и поля → `400 validation_error`.
2. Тип встречи существует → `404 meeting_type_not_found`.
3. Старт внутри окна записи: `start > now`, не дальше 14-го дня
   → `400 slot_out_of_window`.
4. Старт лежит на сетке: 09:00–18:00 по Москве, шаг 30 минут, встреча
   успевает закончиться до 18:00 → `400 slot_out_of_grid`.
5. Нет пересечений с существующими бронями (внутри мьютекса)
   → `409 slot_taken`.

Ответ `201 Created` — бронь:

```json
{
  "id": "6f1c1b8e-6a1e-4b3f-9d0e-2f3c4b5a6978",
  "meetingTypeId": "intro",
  "meetingTypeTitle": "Знакомство",
  "start": "2026-11-12T07:00:00Z",
  "end": "2026-11-12T07:30:00Z",
  "guestName": "Анна",
  "guestEmail": "anna@example.com",
  "createdAt": "2026-11-10T12:00:00Z"
}
```

- `id` брони генерирует сервер (`crypto.randomUUID()`); владелец и гость
  его не задают.
- Ошибки — единый конверт `{ "code": string, "message": string }`.
  Код машинночитаемый, сообщение — для человека и не проверяется тестами.
- При `slot_taken` сообщение объясняет, что время только что заняли,
  и предлагает выбрать другой слот.
- Идемпотентности нет: повторный запрос с тем же слотом вернёт `409`.
  От двойной отправки формы защищает `isSubmitting` на фронтенде.

## 9. Список владельца

`GET /api/bookings` — предстоящие события: только брони со стартом
не раньше текущего момента, отсортированные по `start` по возрастанию.
В одном списке показаны бронирования всех типов встреч, фильтра по типу
нет. Прошедшие брони в список не попадают. Пагинации нет: окно записи
ограничивает объём.

```json
{
  "items": [
    {
      "id": "6f1c1b8e-6a1e-4b3f-9d0e-2f3c4b5a6978",
      "meetingTypeId": "intro",
      "meetingTypeTitle": "Знакомство",

}
```

## 10. Сводка API

| Метод | Путь | Назначение | Успех | Ошибки |
| --- | --- | --- | --- | --- |
| `GET` | `/api/health` | Проверка живости | `200 { status: "ok" }` | — |
| `GET` | `/api/meeting-types` | Список типов встреч | `200 { items: MeetingType[] }` | — |
| `POST` | `/api/meeting-types` | Создать тип встречи | `201 MeetingType` | `400`, `409 meeting_type_exists` |
| `GET` | `/api/availability?meetingTypeId=...` | Сетка на 14 дней | `200 Availability` | `400`, `404 meeting_type_not_found` |
| `POST` | `/api/bookings` | Создать бронь | `201 Booking` | `400`, `404`, `409 slot_taken` |
| `GET` | `/api/bookings` | Предстоящие брони владельца | `200 { items: Booking[] }` | — |

Все ошибки возвращаются в едином конверте
`{ "code": string, "message": string }`.

| Код | HTTP | Когда |
| --- | --- | --- |
| `validation_error` | `400` | Неверная форма запроса или поля |
| `meeting_type_not_found` | `404` | Тип встречи с таким `id` не существует |
| `meeting_type_exists` | `409` | Тип с таким `id` уже создан |
| `slot_out_of_window` | `400` | Старт уже наступил (`start <= now`) или за пределами 14 дней |
| `slot_out_of_grid` | `400` | Старт не на сетке или встреча не успевает до 18:00 |
| `slot_taken` | `409` | Слот пересекается с существующей бронью |

## 11. Экраны

**Гость.**

- `/` — страница типов встреч: название, описание и длительность каждого
  типа, кнопка «Записаться». Если типов нет — пустое состояние.
- `/book?type=intro` — календарь на 14 дней и список слотов выбранного дня
  со статусами «Свободно» / «Занято». В блоке «Информация» видны число
  свободных слотов и длительность.
- «Продолжить» → имя и email → «Подтвердить запись». «Изменить» возвращает
  к выбору времени, не теряя выбранный слот.
- Успех — текст «Бронь подтверждена. До встречи!», слот становится занятым.
- Если у типа нет свободных слотов в окне — список слотов пуст и кнопка
  «Продолжить» неактивна.
- Ошибка `slot_taken` показывает сообщение о том, что слот только что
  заняли, и предлагает выбрать другой.

**Владелец.**

- `/admin` — создание типа встречи: id, название, описание, длительность.
  Ошибка `meeting_type_exists` показывается у поля `id`.
- `/admin/bookings` — раздел «Предстоящие события»: имя и email гостя,
  тип встречи, дата и время слота, дата создания записи. Брони всех типов
  в одном списке.

## 12. Вне объёма

Авторизация и личные кабинеты, отмена и перенос брони, пагинация,
поиск, уведомления по email, хранение между перезапусками,
горизонтальное масштабирование, `Idempotency-Key`, редактирование
и удаление типов встреч.

## 13. Границы тестирования

Проверяем на четырёх уровнях; каждый следующий не заменяет предыдущие.

1. **Юнит-тесты домена.** Сетка слотов, последний старт для 30 и 60 минут,
   встреча, не влезающая до 18:00, границы 14-го дня, прошедшие слоты,
   часовой пояс, матрица пересечений: точное наложение, частичное,
   вложение, касание границами (разрешено), разные типы встреч.
   Время инжектится через `Clock`, поэтому тесты детерминированы.
2. **Контрактные e2e-тесты API.** Прямые HTTP-запросы к NestJS через
   supertest. Каждый ответ валидируется JSON-схемой из `openapi.json`
   через ajv. Покрыты все операции из §10, включая негативные коды:
   `validation_error`, `meeting_type_not_found`, `meeting_type_exists`,
   `slot_out_of_window`, `slot_out_of_grid`, `slot_taken`.
   Отдельный тест конкуренции: `Promise.all` по одному слоту — успешен
   ровно один запрос, остальные получают `409`.
3. **Тесты интерфейса.** React-компоненты на Testing Library: список типов,
   календарь, пустые и ошибочные состояния, блокировка кнопки во время
   отправки. Сетевой слой подменяется на уровне SDK, а не через моки
   `fetch` в каждом тесте.
4. **Браузерный E2E с настоящим сервером.** Playwright запускает собранный
   API и фронтенд на свободных портах, сеть не мокается. Сценарий гостя:
   открыть `/`, увидеть сид-тип «Знакомство», выбрать его, увидеть 14 дней,
   выбрать свободный слот, ввести имя и email, подтвердить, увидеть
   «Бронь подтверждена. До встречи!». Затем владелец открывает
   `/admin/bookings` и видит эту бронь. Отдельный сценарий — конфликт:
   второй гость пытается занять тот же слот и видит сообщение о занятости.

Ручная проверка — запись сквозного сценария в asciinema (issue #12).
Нагрузочное тестирование, проверка нескольких процессов и горизонтального
масштабирования, сохранность данных после перезапуска и доставка email
в границы тестирования не входят.
