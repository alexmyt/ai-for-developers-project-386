# 0002 — Contract-first API на TypeSpec

- **Статус:** принято
- **Дата:** 2026-11-04

## Контекст

Требования обязывают иметь TypeSpec-контракт, сгенерированную
OpenAPI-спецификацию и клиентский SDK для фронтенда. Серверные типы
и маршруты можно генерировать только там, где фреймворк это поддерживает;
при отсутствии серверного генератора бэкенд пишется по контракту
и проверяется тестами.

Проверенные факты на момент решения:

- серверного генератора для NestJS нет: генератор `typescript-nestjs`
  в openapi-generator помечен как *client* и *experimental* и создаёт
  HTTP-клиент, а не контроллеры NestJS;
- генераторы клиента для TypeScript живы и поддерживают OpenAPI 3.0:
  `@hey-api/openapi-ts` 0.99, `orval` 8, `openapi-typescript` 7.

## Решение

1. **Источник истины — TypeSpec.** Контракт лежит в `packages/contract`,
   эмиттер `@typespec/openapi3` генерирует `openapi.json` в версии 3.0
   (максимальная совместимость с генераторами клиента).
2. **`openapi.json` коммитится.** Диффы контракта видны в ревью, спецификация
   доступна без запуска сборки. CI перегенерирует её и падает, если файл
   в репозитории устарел (`git diff --exit-code`).
3. **Клиент генерируется** из `openapi.json` через `@hey-api/openapi-ts`
   с плагинами TypeScript, TanStack Query и Zod. Пакет `packages/sdk`
   не редактируется руками.
4. **Сервер пишется руками** по контракту: DTO, контроллеры и сериализация
   в NestJS. Соответствие проверяется контрактными e2e-тестами: каждый ответ
   валидируется JSON-схемой из `openapi.json` через ajv, плюс отдельные
   тесты на коды ошибок и на пересечения интервалов.
5. **`operationId` задаются явно** (`listMeetingTypes`, `getAvailability`,
   `createBooking`, `listBookings`, `createMeetingType`) — от них зависят
   имена сгенерированных хуков.

API целиком живёт под `/api`; сгенерированный клиент конфигурируется
с `baseUrl: '/api'`.

## Рассмотренные альтернативы

- **`@nestjs/swagger` (код → OpenAPI)** — нарушает требование «TypeSpec —
  источник истины»: спека стала бы производной от декораторов.
- **Генерация серверных стабов из OpenAPI** — подходящего генератора для
  NestJS нет; генератор `typescript-nestjs` создаёт клиент и не покрывает
  контроллеры, DTO-валидацию и DI.
- **Orval** — генерирует React Query-хуки, но оставляет меньше контроля над
  итоговым клиентом и требует mutator для базового URL.
- **`openapi-typescript`** — даёт только типы, всю обвязку запросов пришлось
  бы писать руками.
- **OpenAPI 3.1** — часть генераторов клиента поддерживает её не полностью;
  выгоды для этого контракта нет.

## Последствия

- Изменение API начинается с правки `.tsp`, а не с кода; порядок —
  контракт → `openapi.json` → SDK → реализация → тесты.
- Контрактные тесты — единственная гарантия соответствия сервера спеке,
  поэтому они обязательны для каждого эндпоинта, включая негативные сценарии.
- Сгенерированные файлы (`openapi.json`, `packages/sdk`) не правятся руками;
  их расхождение с TypeSpec ловит CI.

## Поправка от 2026-11-11

Пункт 3 решения обещал плагины TanStack Query и Zod — SDK сгенерирован
без них: только TypeScript-типы и Fetch-клиент. Экраны карты билетов
работают на обычных эффектах с точечным поллингом, а формы —
контролируемые компоненты, поэтому сгенерированные хуки и схемы пока
не пригодились (см. поправку в ADR-0001). Вернуться к плагинам стоит,
когда на фронтенде появится серверное состояние сложнее точечного
поллинга или понадобится клиентская валидация по схемам контракта.
