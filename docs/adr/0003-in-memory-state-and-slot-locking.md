# 0003 — Состояние в памяти и защита от двойного бронирования

- **Статус:** принято
- **Дата:** 2026-11-04

## Контекст

База данных не нужна: состояние хранится в памяти процесса. При этом
сценарий требует, чтобы один интервал нельзя было занять дважды, включая
частичные наложения разных типов встреч, и чтобы правило соблюдалось при
одновременных запросах. Следующая встреча может начинаться ровно в момент
окончания предыдущей.

## Решение

- **Хранилище** — `Map` в памяти процесса: типы встреч и брони. При старте
  загружается один сид-тип «Знакомство» (30 минут), чтобы гостевой флоу
  работал сразу после `docker run`.
- **Интервалы полуоткрытые:** `[start, end)`. Пересечение — это
  `a.start < b.end && b.start < a.end`; касание границ конфликтом не считается.
- **Мьютекс по дате.** Бронирования сериализуются `async-mutex` по ключу
  даты слота; проверка пересечений и вставка выполняются синхронно внутри
  критической секции, без `await` между ними. Разные дни не блокируют
  друг друга.
- **`POST /api/bookings` не принимает `end`:** длительность берётся из типа
  встречи, поэтому клиент не может подделать интервал. Конфликт возвращается
  как `409` с кодом `slot_taken`.
- **Время инжектится.** Доступ к текущему времени идёт через `Clock`-провайдер,
  а не через `Date.now()` напрямую: иначе тесты на 14-дневное окно и на
  отфильтрованные прошедшие слоты зависят от календарной даты запуска.
- **Идемпотентности нет.** `Idempotency-Key` не вводится — вне объёма
  сценария; от двойной отправки формы защищает состояние `isSubmitting`
  на фронтенде.

## Рассмотренные альтернативы

- **Глобальный мьютекс** — проще, но сериализует все бронирования, хотя
  конфликт возможен только внутри одного дня.
- **Проверка без блокировки** — в одном процессе её достаточно, пока между
  проверкой и вставкой нет `await`; мьютекс делает это правило явным
  и защищает от будущих правок с асинхронными вызовами.
- **`Idempotency-Key`** — потребовал бы хранения ключей и отдельной модели
  ошибок, которых нет в требованиях.
- **Оптимистичные версии / транзакции** — нет хранилища, которое могло бы
  их поддержать.

## Последствия

- Сервис рассчитан на один процесс и один реплику: при горизонтальном
  масштабировании мьютекс в памяти перестанет защищать, и понадобится
  внешнее хранилище. Это осознанное ограничение учебного проекта.
- Все данные теряются при перезапуске контейнера.
- Тесты конкуренции выполняются через `Promise.all` по одному и тому же
  слоту и проверяют, что успешен ровно один запрос.
