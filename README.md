## Сценарий работы

«Запись на звонок» — упрощённый сервис бронирования по мотивам Cal.com: владелец публикует доступное время, гость выбирает свободный слот и записывается. Авторизации и личных кабинетов нет, владелец календаря один и задан заранее.

1. **Тип встречи.** Владелец создаёт тип встречи: название, описание и длительность. Длительность определяет размер слота (например, 30 минут).
2. **Выбор типа.** Гость открывает «Записаться» и выбирает тип встречи. Приложение показывает календарь на ближайшие 14 дней; часы работы, часовой пояс и шаг стартов зафиксированы в спецификации.
3. **Дата и слот.** Гость выбирает дату в календаре — справа появляется список слотов дня со статусами «Свободно» / «Занято», а в блоке «Информация» видны число свободных слотов и длительность.
4. **Подтверждение.** Гость выбирает свободный слот, нажимает «Продолжить», вводит имя и email и нажимает «Подтвердить запись». Кнопка «Изменить» возвращает к выбору времени.
5. **Проверка конфликта.** Один интервал нельзя занять дважды: пересечения запрещены, включая частичные наложения разных типов; следующая встреча может начинаться ровно в момент окончания предыдущей. Правило действует и при одновременных запросах.
6. **Успех.** Гость видит «Бронь подтверждена. До встречи!», слот получает статус «Занято» и пропадает из свободных.
7. **Список владельца.** Запись сразу появляется в разделе «Предстоящие события»: имя и email гостя, тип встречи, дата и время слота, дата создания записи.

## Стек

Монорепо на pnpm workspaces:

| Пакет | Что внутри |
| --- | --- |
| `apps/api` | NestJS 12, состояние в памяти, раздача статики |
| `apps/web` | React 19 + Vite 8, SPA для гостя и владельца |
| `packages/contract` | TypeSpec 1.17, из него генерируется `openapi.json` (OpenAPI 3.0) |
| `packages/sdk` | клиент для фронтенда, сгенерированный из `openapi.json` |

- **Контракт** — TypeSpec как источник истины. `openapi.json` коммитится,
  CI проверяет, что он не устарел. Серверного генератора для NestJS нет,
  поэтому бэкенд написан по контракту и проверяется контрактными
  e2e-тестами (supertest + валидация ответов по JSON-схеме через ajv).
- **Фронтенд** — React 19, Vite, `react-router`, TanStack Query, Tailwind CSS
  + shadcn/ui, React Hook Form + Zod, `date-fns`.
- **Бэкенд** — NestJS 12, Express, `async-mutex` для защиты от двойного
  бронирования, Vitest для тестов.
- **Доставка** — один multi-stage Docker-образ (`node:22-alpine`), NestJS
  отдаёт и API, и собранную статику; API под `/api`, порт 3000,
  HEALTHCHECK на `/api/health`.

Авторизации нет по условиям сценария: владельческие эндпоинты
(`POST /api/meeting-types`, `GET /api/bookings`) открыты, а состояние
хранится в памяти одного процесса и теряется при перезапуске.

Решения и их обоснование — в [ADR](docs/adr/): [стек](docs/adr/0001-stack.md),
[contract-first API](docs/adr/0002-contract-first-api.md),
[состояние в памяти и блокировки](docs/adr/0003-in-memory-state-and-slot-locking.md).
