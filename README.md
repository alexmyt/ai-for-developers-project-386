Разработайте совместно с ИИ сервис для бронирования календаря

Учебный проект Хекслета: https://ru.hexlet.io/programs/ai-for-developers

## Демо

Приложение развёрнуто на Render: **https://call-calendar-zfmn.onrender.com**.
Гость открывает главную страницу, владелец —
[/admin](https://call-calendar-zfmn.onrender.com/admin).

## Сценарий работы

«Запись на звонок» — упрощённый сервис бронирования по мотивам Cal.com: владелец публикует доступное время, гость выбирает свободный слот и записывается. Авторизации и личных кабинетов нет, владелец календаря один и задан заранее.

1. **Тип встречи.** Владелец создаёт тип встречи: id, название, описание и длительность. Длительность определяет размер слота (например, 30 минут).
2. **Выбор типа.** Гость открывает «Записаться» и выбирает тип встречи. Приложение показывает календарь на ближайшие 14 дней; часы работы, часовой пояс и шаг стартов зафиксированы в [спецификации](docs/spec/calendar.md).
3. **Дата и слот.** Гость выбирает дату в календаре — справа появляется список слотов дня со статусами «Свободно» / «Занято», а в блоке «Информация» видны число свободных слотов и длительность.
4. **Подтверждение.** Гость выбирает свободный слот, нажимает «Продолжить», вводит имя и email и нажимает «Подтвердить запись». Кнопка «Изменить» возвращает к выбору времени.
5. **Проверка конфликта.** Один интервал нельзя занять дважды: пересечения запрещены, включая частичные наложения разных типов; следующая встреча может начинаться ровно в момент окончания предыдущей. Правило действует и при одновременных запросах.
6. **Успех.** Гость видит «Бронь подтверждена. До встречи!», слот получает статус «Занято» и пропадает из свободных.
7. **Список владельца.** Запись сразу появляется в разделе «Предстоящие события»: имя и email гостя, тип встречи, дата и время слота, дата создания записи.

## Стек

Монорепо на pnpm workspaces:

| Пакет | Что внутри |
| --- | --- |
| `apps/api` | NestJS 12, состояние в памяти, раздача статики |
| `apps/web` | React 19 + Vite 8, SPA для гостя и владельца |
| `packages/contract` | TypeSpec 1.17, из него генерируется `openapi.json` (OpenAPI 3.0) |
| `packages/sdk` | клиент для фронтенда, сгенерированный из `openapi.json` |

- **Контракт** — TypeSpec как источник истины. `openapi.json` коммитится,
  CI проверяет, что он не устарел. Серверного генератора для NestJS нет,
  поэтому бэкенд написан по контракту и проверяется контрактными
  e2e-тестами (supertest + валидация ответов по JSON-схеме через ajv).
- **Фронтенд** — React 19, Vite, `react-router`, TanStack Query, Tailwind CSS
  + shadcn/ui, React Hook Form + Zod, `date-fns`.
- **Бэкенд** — NestJS 12, Express, `async-mutex` для защиты от двойного
  бронирования, Vitest для тестов.
- **Доставка** — один multi-stage Docker-образ (`node:22-alpine`), NestJS
  отдаёт и API, и собранную статику; API под `/api`, порт 3000,
  HEALTHCHECK на `/api/health`.

Авторизации нет по условиям сценария: владельческие эндпоинты
(`POST /api/meeting-types`, `GET /api/bookings`) открыты, а состояние
хранится в памяти одного процесса и теряется при перезапуске.

Решения и их обоснование — в [ADR](docs/adr/): [стек](docs/adr/0001-stack.md),
[contract-first API](docs/adr/0002-contract-first-api.md),
[состояние в памяти и блокировки](docs/adr/0003-in-memory-state-and-slot-locking.md),
[деплой на Render](docs/adr/0004-render-deployment.md).
Правила календаря — таймзона, часы работы, сетка слотов, окно записи
и запрет пересечений — в [спецификации](docs/spec/calendar.md),
термины проекта — в [глоссарии](GLOSSARY.md).

## Установка

Понадобится [mise](https://mise.jdx.dev): он устанавливает Node.js и pnpm
нужных версий.

```bash
curl https://mise.run | sh
# или
brew install mise
```

Активируйте mise в shell (один раз):

```bash
echo 'eval "$(mise activate zsh)"' >> ~/.zshrc
```

Затем клонируйте репозиторий и установите инструменты и зависимости:

```bash
git clone https://github.com/alexmyt/ai-for-developers-project-386.git
cd ai-for-developers-project-386
mise run setup
```

`mise run setup` ставит инструменты из `mise.toml`, зависимости и git-хуки.
Проверить, что инструменты подхватились, можно командой `mise doctor`.

## Использование

```bash
pnpm dev          # API на :3000 и Vite на :5173, /api проксируется в API
mise run check    # все проверки: формат, линтер, типы, тесты, сборка, контракт, SDK, браузерный e2e
mise run generate # TypeSpec → openapi.json → SDK одной командой
pnpm test         # Vitest: контрактные и юнит-тесты
pnpm lint         # ESLint
pnpm typecheck    # tsc --noEmit во всех пакетах
pnpm build        # контракт → openapi.json, затем API и веб
```

Проверка живости API: `curl http://localhost:3000/api/health` →
`{"status":"ok"}`. Границы тестирования — в
[спецификации](docs/spec/calendar.md#13-границы-тестирования): юнит-тесты,
контрактные e2e, тесты интерфейса и браузерный Playwright-сценарий
с настоящим сервером.

## Деплой

Сервис живёт на Render и описывается blueprint-файлом
[render.yaml](render.yaml): один Docker-контейнер отдаёт и API, и собранную
статику (ADR-0002), план Free, регион Frankfurt, health check на
`/api/health`. Обоснование — в [ADR-0004](docs/adr/0004-render-deployment.md),
подключение MCP-сервера Render к агентам — в
[docs/agents/render.md](docs/agents/render.md). Push в `main` запускает
автодеплой.

**Данные не сохраняются между перезапусками.** Состояние хранится в памяти
процесса (ADR-0003), поэтому рестарт, редеплой и засыпание Free-инстанса
после ~15 минут неактивности стирают все типы встреч и брони; остаётся
только сид-тип «Знакомство». Публичная ссылка при этом не меняется, а
первый запрос после засыпания будит инстанс до минуты.

Прогнать сценарий по публичной ссылке:

```bash
E2E_BASE_URL=https://call-calendar-zfmn.onrender.com pnpm e2e
```
